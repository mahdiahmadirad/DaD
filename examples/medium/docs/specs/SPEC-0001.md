# SPEC-0001: Partner webhook acceptance

## Status

Approved

## Purpose

Define the request and response behavior by which Relay accepts shipment events
into its durable inbox.

## Scope

- authentication and envelope validation;
- durable acceptance and duplicate handling; and
- the receipt returned to a partner.

## Out of scope

- downstream event processing;
- partner provisioning; and
- inbox retention policy.

## Requirements

1. Relay accepts `POST /partner-events` with a JSON event envelope containing
   non-empty `partner_id`, `event_id`, `event_type`, and `occurred_at` fields.
2. Relay authenticates the request before storing its payload.
3. Relay acknowledges a new event only after the inbox transaction commits.
4. `(partner_id, event_id)` uniquely identifies an accepted event.
5. A duplicate returns the receipt of the existing event and creates no new
   inbox record.
6. The response does not depend on downstream processing completing.

## Interfaces and behavior

For a newly committed event, Relay returns status `202` and:

```json
{"receipt_id":"<stable identifier>","duplicate":false}
```

For an already accepted identity, Relay returns status `202` with the original
`receipt_id` and `duplicate` set to `true`.

An unauthenticated request returns `401`. An authenticated request with an
invalid envelope returns `400`. A request that cannot be durably committed
returns a non-`2xx` response and must not claim a receipt.

## Acceptance criteria

- Contract tests cover new, duplicate, unauthenticated, invalid, and
  persistence-failure requests.
- A duplicate produces one stored inbox event and one stable receipt.
- A simulated failure before commit produces no acknowledgement.
- Downstream processing is not invoked in the request transaction.
