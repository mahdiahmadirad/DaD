# SPEC-0002: CLI commands and repository behavior

## Status

Approved

## Purpose

Define the DaD CLI v1 command surface for initializing DaD support files,
creating governed documents, inspecting repository state, resolving task
context, checking document mechanics, and retrieving official prompts.

## Scope

- command names, arguments, and results;
- deterministic initialization of reusable DaD files;
- ADR, SPEC, and TASK creation;
- document inventory and repository status;
- task-context resolution;
- structural documentation checks; and
- access to the official DaD prompts.

## Out of scope

- approving or rejecting project decisions;
- deciding whether project architecture or behavior is correct;
- generating project-specific content with an AI model;
- implementing, testing, or modifying product code;
- automatically reconciling documentation with implementation;
- editing document lifecycle status;
- watching the filesystem or running as a service;
- version-control, issue-tracker, or hosting-provider operations; and
- installation and update behavior.

## Requirements

### Command surface

The v1 CLI provides:

| Command | Purpose | Mutates files |
| --- | --- | --- |
| `dad init [path]` | Install canonical reusable DaD support files | Yes |
| `dad new <type> --title <title>` | Create an ADR, SPEC, or TASK | Yes |
| `dad list [type]` | List governed documents | No |
| `dad status` | Summarize document state and mechanical health | No |
| `dad context <task-id>` | Resolve governing context for a TASK | No |
| `dad check [document-id...]` | Check document mechanics | No |
| `dad prompt list` | List official prompt names | No |
| `dad prompt show <name>` | Print one official prompt | No |

All commands follow the platform and interface contract in
[SPEC-0001](SPEC-0001.md).

### Common document behavior

- **CLI-DOC-001:** ADRs use `docs/adr/ADR-NNNN.md`, SPECs use
  `docs/specs/SPEC-NNNN.md`, and TASKs use `docs/tasks/TASK-NNNN.md`.
- **CLI-DOC-002:** Templates and general documentation are excluded from
  numbered document inventories.
- **CLI-DOC-003:** Identifiers are canonical uppercase `TYPE-NNNN` values.
  User input is accepted case-insensitively and normalized in output.
- **CLI-DOC-004:** Titles are trimmed, non-empty, single-line text. A title does
  not affect the canonical filename.
- **CLI-DOC-005:** Document discovery must reject duplicate identifiers,
  including duplicates that differ only by path or letter case.
- **CLI-DOC-006:** Lists are sorted by type in `ADR`, `SPEC`, `TASK` order and
  then by numeric identifier unless a command defines a narrower order.
- **CLI-DOC-007:** Project-local templates take precedence over templates
  bundled with the CLI. A malformed local template is an error, not a reason
  to silently use the bundled version.
- **CLI-DOC-008:** The CLI preserves document authority boundaries. It does not
  infer an ADR, SPEC, status transition, or completion claim from source code
  or conversation history.

## Interfaces and behavior

### `dad init`

```text
dad init [path] [--dry-run]
```

`path` defaults to the current working directory. Initialization does not use
normal DaD root discovery because it operates on a repository being adopted.

Preconditions:

- the target exists and is a directory;
- `PROJECT-VISION.md` and `AGENTS.md` exist and are non-empty; and
- every intended target can be created or is byte-identical to the bundled
  canonical file.

The command installs missing copies of:

```text
docs/
├── DOCUMENTATION.md
└── templates/
    ├── ADR-TEMPLATE.md
    ├── SPEC-TEMPLATE.md
    └── TASK-TEMPLATE.md
```

It does not create project-specific ADRs, SPECs, TASKs, vision content, working
rules, source code, CI, or empty `docs/adr`, `docs/specs`, or `docs/tasks`
directories. Those document directories are created when the first document of
that type is created.

If the required project vision or working agreement is absent, the command
exits with code `3` and directs the user to
`dad prompt show project-bootstrap`. If a target support file exists with
different content, initialization exits with code `4` before writing and lists
every conflict. An identical file is reported as unchanged.

Initialization is idempotent. A second run against an initialized repository
produces no changes and exits successfully.

JSON `data` contains `root` and ordered `created`, `unchanged`, and `conflicts`
path arrays.

### `dad new`

```text
dad new adr  --title <title> [--number NNNN] [--dry-run]
dad new spec --title <title> [--number NNNN] [--dry-run]
dad new task --title <title> [--number NNNN] [--dry-run]
```

The command:

1. resolves the repository;
2. validates the selected template;
3. allocates or validates the identifier;
4. creates the document's parent directory when needed;
5. replaces only the template identifier and title placeholders; and
6. writes one new document.

Default allocation is one greater than the greatest identifier present for
that type. DaD lifecycle records are not deleted, so a conforming repository
retains every previously used number. `TASK-0000` remains reserved for
repository bootstrap; if no TASK number exists, normal TASK allocation begins
at `0001`.

`--number` requests an explicit four-digit number. It is accepted only when the
identifier is unused, greater than every identifier present for that type, and
is not the reserved `TASK-0000`. Gaps are allowed.

New ADRs have `Proposed` status, new SPECs have `Draft` status, and new TASKs
have `Proposed` status, as defined by the canonical templates. The CLI does not
transition them to an authoritative or actionable state.

Creation must be safe under concurrent allocation as required by SPEC-0001.
Success output includes the canonical identifier and repository-relative path.
JSON `data` contains `id`, `type`, `title`, `path`, `status`, and `created`.
During `--dry-run`, `created` is `false` and no directory or file is written.

### `dad list`

```text
dad list [adr|spec|task] [--status <status>]
```

With no type, the command lists all governed documents. `--status` filters by
an allowed status for the selected type; without a type it accepts any
canonical ADR, SPEC, or TASK status.

Each result contains:

- canonical identifier;
- type;
- status;
- title; and
- repository-relative path.

Documents whose identity, title, or status cannot be parsed are omitted from
the normal result and reported as error diagnostics. Their presence makes the
command exit with code `1`.

Text output uses one document per line. JSON `data.documents` is an ordered
array with the fields above.

### `dad status`

```text
dad status
```

The command reports:

- resolved repository root;
- counts by document type and lifecycle status;
- TASKs currently `Ready`, `In Progress`, or `Blocked`;
- counts of structural errors and warnings from the same rules as
  `dad check`; and
- whether required core files and canonical templates are present.

Status is an inventory, not a claim that the software or project is complete.
It must not infer implementation progress from version-control state or the
presence of source files.

The command exits with code `1` when structural errors exist and `0` when only
warnings or no findings exist. JSON `data` contains `root`, `counts`,
`actionable_tasks`, `blocked_tasks`, and `check_summary`.

### `dad context`

```text
dad context <task-id>
```

The command resolves the smallest explicit document set governing one TASK. It
does not infer context from source-code imports, issue trackers, or
conversation history.

Resolution includes:

1. `PROJECT-VISION.md`;
2. every `AGENTS.md` applying from the repository root through the TASK's
   directory, ordered broadest to most specific;
3. the requested TASK;
4. TASKs directly referenced by the requested TASK;
5. accepted ADRs directly referenced by the TASK or by a referenced SPEC; and
6. approved SPECs directly referenced by the TASK.

References are resolved from Markdown links in the TASK's `References`
section and the `References` sections of its directly referenced SPECs.
Duplicate documents are emitted once. ADRs and SPECs are ordered numerically
within their type; referenced TASKs are ordered numerically and their current
status is reported.

A missing reference, duplicate identifier, malformed relationship, referenced
ADR not in `Accepted` status, or referenced SPEC not in `Approved` status is an
error. Historical TASK inspection remains allowed for every TASK status, and
the output always reports the TASK status.

Text output lists each path with its role and relationship. JSON
`data.documents` contains ordered objects with `id` when applicable, `path`,
`role`, `status` when applicable, and `required_by`.

The command does not concatenate document contents, execute a prompt, or claim
that inferred code and tests are part of the resolved context.

### `dad check`

```text
dad check [document-id...] [--strict]
```

With no identifiers, the command checks the full DaD document set. With
identifiers, it checks those documents and the references necessary to
evaluate them. Templates are checked as templates and are never treated as
numbered project documents.

Errors include:

- missing `PROJECT-VISION.md` or root `AGENTS.md`;
- invalid or duplicate document identifiers;
- non-canonical numbered filenames;
- heading identifier or title missing or inconsistent with the filename;
- missing or invalid lifecycle status;
- broken local Markdown references;
- a governing reference to an ADR or SPEC without an authoritative status;
- invalid supersession or replacement references;
- a `Complete` TASK with no substantive completion evidence;
- unresolved template identifiers in a numbered document; and
- a reference that resolves outside the repository root.

Warnings include:

- a `Ready` or `In Progress` TASK with no acceptance conditions;
- a `Blocked`, `Cancelled`, `Rejected`, `Withdrawn`, or `Retired` document
  without an explanatory note;
- duplicated normative wording that can be identified mechanically only when
  it is exact; and
- a local template that omits a required canonical section.

The command checks structure and explicit relationships only. It must state
that it does not prove architectural correctness, behavioral conformance,
documentation freshness, implementation completeness, or security.

Errors produce exit code `1`. Warnings alone produce exit code `0`, or `1`
with `--strict`. JSON `data.summary` contains counts by severity and
`data.checked_documents` contains ordered canonical identifiers.

### `dad prompt`

```text
dad prompt list
dad prompt show <name>
```

Official names are:

- `project-bootstrap`;
- `architecture-discovery`;
- `documentation-audit`;
- `task-implementation`; and
- `documentation-reconciliation`.

Prompt commands read the immutable prompt resources bundled with the installed
CLI release. They do not require or discover a repository and do not prefer
project-local files with the same name.

`list` returns names in the order above with a one-line purpose. `show` writes
the complete UTF-8 Markdown prompt to standard output without a surrounding
code fence, interpolation, or execution. Unknown names are usage errors.

JSON output for `show` contains `name`, `content`, and the CLI release version
that supplied it. The CLI never sends prompt content or repository data to an
agent or network service.

## Acceptance criteria

- Every command implements the syntax, output data, mutation boundary, and exit
  behavior defined above.
- `init` is idempotent, performs no project-specific generation, refuses
  conflicting support files before writing, and creates no empty future
  directories.
- `new` allocates independent stable sequences, respects explicit available
  numbers, uses canonical templates, and creates exactly one document.
- `list` and `status` return deterministic results for valid, malformed,
  incomplete, and empty document sets.
- `context` resolves the same ordered authority set on Windows, Linux, and
  macOS and rejects missing or non-authoritative governing references.
- `check` has fixtures for every listed error and warning, including strict
  warning behavior and references that escape the root.
- `prompt list` exposes exactly the five official prompt names and `prompt
  show` returns byte-identical bundled prompt content on all platforms.
- No command invokes an AI model, requires a network or version-control client,
  modifies product code, changes lifecycle authority, or performs
  version-control operations.
- The full command suite satisfies every cross-platform acceptance criterion in
  SPEC-0001.
