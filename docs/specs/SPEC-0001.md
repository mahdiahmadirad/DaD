# SPEC-0001: CLI platform and interface contract

## Status

Draft

## Purpose

Define the portable public contract shared by every DaD command-line
operation. The contract makes the CLI predictable for people, scripts, and AI
coding agents on Windows, Linux, and macOS without making DaD dependent on any
of them.

## Scope

- executable invocation and supported environments;
- repository-root discovery;
- global options;
- human-readable and machine-readable output;
- diagnostic and exit-code behavior;
- deterministic and safe filesystem behavior; and
- cross-platform acceptance requirements.

## Out of scope

- implementation language, libraries, and internal architecture;
- packaging, installation, update, and release channels;
- command-specific behavior defined by
  [SPEC-0002](SPEC-0002.md);
- graphical interfaces or background services;
- invoking an AI model or coding agent;
- semantic judgment about architecture or documentation quality; and
- network or hosted-repository operations.

## Requirements

### Platform support

- **CLI-PLAT-001:** The public executable name must be `dad`. A native Windows
  executable may be stored as `dad.exe`, but normal invocation remains `dad`.
- **CLI-PLAT-002:** Every command must provide equivalent behavior on Windows,
  Linux, and macOS.
- **CLI-PLAT-003:** Windows support must not require Windows Subsystem for
  Linux, a POSIX compatibility layer, or a Unix shell.
- **CLI-PLAT-004:** Human-readable invocation must work from PowerShell and
  Command Prompt on Windows and from common POSIX-compatible shells on Linux
  and macOS.
- **CLI-PLAT-005:** A release must publish the tested operating-system versions
  for all three platform families. Removing a platform family requires a
  superseding approved specification.
- **CLI-PLAT-006:** Core commands must operate without network access, a
  version-control client, or an AI service.

### Repository discovery

- **CLI-ROOT-001:** Commands that operate on a DaD repository must resolve
  exactly one repository root.
- **CLI-ROOT-002:** Root resolution precedence is:
  1. the `--root <path>` option;
  2. the `DAD_ROOT` environment variable; then
  3. upward discovery starting at the current working directory.
- **CLI-ROOT-003:** A discovered DaD root is the nearest ancestor containing
  both `PROJECT-VISION.md` and `AGENTS.md`.
- **CLI-ROOT-004:** An explicit relative root is resolved against the current
  working directory. The CLI reports the resolved absolute root in
  human-readable output when ambiguity would otherwise be possible.
- **CLI-ROOT-005:** Root discovery must not require a `.git` directory and must
  not cross above the filesystem root.
- **CLI-ROOT-006:** A missing, inaccessible, or ambiguous root is an error. The
  CLI must not guess a different repository based on similarly named files.
- **CLI-ROOT-007:** `dad --help`, `dad --version`, and official prompt
  inspection do not require a repository root.

### Paths and text

- **CLI-PATH-001:** The CLI must accept platform-native absolute and relative
  paths, including Windows drive-letter and UNC paths where the operating
  system grants access.
- **CLI-PATH-002:** Paths containing spaces and non-ASCII characters must
  behave the same as paths containing only ASCII characters.
- **CLI-PATH-003:** Repository-relative paths in machine-readable output use
  `/` as the separator on every platform. Human-readable output may use native
  separators.
- **CLI-PATH-004:** Document identifiers and canonical filenames are compared
  case-insensitively for collision detection, even on case-sensitive
  filesystems.
- **CLI-TEXT-001:** Markdown created by the CLI must be UTF-8 without a byte
  order mark and use LF line endings on every platform.
- **CLI-TEXT-002:** A targeted edit to an existing UTF-8 document must preserve
  its existing line-ending convention and unrelated content.
- **CLI-TEXT-003:** Invalid text encoding is reported without rewriting the
  file.

### Global options

The CLI must support:

| Option | Behavior |
| --- | --- |
| `--root <path>` | Select the repository root explicitly |
| `--format text\|json` | Select human-readable or machine-readable output |
| `--no-color` | Disable terminal color |
| `--quiet` | Suppress nonessential successful text output |
| `--dry-run` | Preview a mutating command without writing |
| `--help` | Show help for the selected command |
| `--version` | Show the CLI version |

- **CLI-OPT-001:** `text` is the default output format.
- **CLI-OPT-002:** `--dry-run` is accepted only by commands that can mutate the
  filesystem; using it elsewhere is a usage error.
- **CLI-OPT-003:** The `NO_COLOR` environment variable and `--no-color`
  disable color. `--no-color` takes precedence over any future color setting.
- **CLI-OPT-004:** Color is used only when text output is attached to a
  compatible terminal. Color never changes the wording or meaning of output.
- **CLI-OPT-005:** Global options have the same names and semantics for every
  command that supports them.

## Interfaces and behavior

### Text output

Successful primary results are written to standard output. Diagnostics,
warnings, and operational errors are written to standard error. Help and
version text are written to standard output.

Text output must:

- use clear language without requiring knowledge of internal implementation;
- identify documents by canonical identifier and repository-relative path;
- remain understandable without color;
- avoid progress animation when output is not an interactive terminal; and
- sort inventories and diagnostics deterministically.

`--quiet` suppresses explanatory success messages but not explicitly requested
data, warnings, or errors. It affects text output only.

### JSON output

`--format json` writes exactly one UTF-8 JSON object followed by one newline to
standard output. It uses this envelope:

```json
{
  "schema_version": "1",
  "command": "check",
  "success": true,
  "data": {},
  "diagnostics": []
}
```

- `schema_version` identifies the output contract, independent of the CLI
  release version.
- `command` is the canonical command name.
- `success` states whether the command satisfied its success condition.
- `data` contains command-specific results.
- `diagnostics` is an ordered array of diagnostic objects.

A diagnostic object contains:

```json
{
  "code": "DAD-CHECK-001",
  "severity": "error",
  "message": "Referenced document does not exist.",
  "path": "TASK-0003.md",
  "line": 24,
  "column": 3
}
```

`code`, `severity`, and `message` are required. `path`, `line`, and `column`
are included only when known. Severity is `error`, `warning`, or `info`.
Machine-readable output contains no color, progress animation, or
platform-dependent path separators for repository files.

In JSON mode, command diagnostics appear in the JSON envelope and are not
duplicated on standard error. Standard error is used only when the process
cannot construct a valid envelope, such as a failure before argument parsing
or JSON serialization.

Additive fields may be introduced within schema version `1`. Removing a field,
changing its type or meaning, or changing exit-code semantics requires a new
schema version.

### Exit codes

| Code | Meaning |
| ---: | --- |
| `0` | Command completed and its success condition was satisfied |
| `1` | Documents or repository state failed the requested check |
| `2` | Invalid command syntax, option, or argument |
| `3` | DaD root missing, invalid, or inaccessible |
| `4` | Mutation refused because of a conflict or safety condition |
| `5` | Filesystem input/output failure |
| `6` | Unexpected internal failure |
| `130` | Operation interrupted by the user |

The same condition produces the same exit code on every supported platform.
JSON `success` is `true` only for exit code `0`. A command must not report a
successful mutation when any requested write failed.

Diagnostic codes are stable identifiers. Message wording may improve without
changing a code, but one code must continue to represent the same condition.

### Filesystem safety

Mutating commands must:

1. inspect every target and conflict before the first intended write where
   practical;
2. refuse to overwrite an existing non-identical file unless the
   command-specific contract explicitly permits a targeted edit;
3. write each document atomically by creating a sibling temporary file and
   replacing the target only after the complete content is durable;
4. remove temporary files after failure when safe;
5. refuse a resolved write target outside the selected repository root;
6. produce no writes during `--dry-run`; and
7. report every file created, changed, skipped, or refused.

Number allocation and file creation must be concurrency-safe. Two concurrent
creations must receive distinct available identifiers, or one must exit with a
conflict before producing a partial document.

Commands must not modify version-control state, commit, push, invoke hooks, or
change repository configuration.

### Determinism

Given the same repository bytes, arguments, environment options defined by this
specification, and CLI version, a command must produce the same document
content and logically equivalent output on Windows, Linux, and macOS.

Absolute roots, native human-readable separators, terminal capabilities, and
documented release-version fields may vary by environment. Repository-relative
JSON paths, identifiers, ordering, diagnostics, and created Markdown must not.

## Acceptance criteria

- The complete command acceptance suite passes on published supported versions
  of Windows, Linux, and macOS.
- Windows tests exercise both PowerShell and Command Prompt without WSL.
- Linux and macOS tests exercise a POSIX-compatible shell.
- Root discovery passes from the root, nested directories, explicit relative
  and absolute roots, `DAD_ROOT`, paths with spaces, Unicode paths, Windows
  drive paths, and UNC paths where available.
- Text and JSON golden tests demonstrate stable ordering, stream selection,
  path normalization, diagnostic shape, and exit codes.
- Mutation tests demonstrate atomic writes, collision refusal, concurrency-safe
  number allocation, dry-run behavior, interruption safety, and refusal to
  write outside the root.
- The same fixture produces byte-identical new Markdown files on all three
  platform families.
- All core command tests pass with network access disabled and outside a
  version-controlled repository.
