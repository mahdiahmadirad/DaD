# SPEC-0003: CLI release and distribution contract

## Status

Draft

## Purpose

Define how a reviewed DaD CLI source revision becomes a versioned,
cross-platform, verifiable, and immutable public release. This contract gives
maintainers a repeatable release process and gives users predictable artifacts
without changing the offline or agent-neutral CLI runtime.

## Scope

- release-version authority and compatibility rules;
- development and release version reporting;
- changelog structure and release notes;
- release triggers and validation gates;
- supported operating-system and architecture targets;
- archive naming and contents;
- checksums, provenance, and immutability;
- GitHub Release publication; and
- installation guidance for direct archive downloads and versioned Go builds.

## Out of scope

- macOS signing and notarization;
- Windows code signing;
- installers and automatic update behavior;
- Homebrew, Winget, Scoop, Chocolatey, Linux repository, or other
  package-manager publication;
- containers, mobile targets, and graphical applications;
- nightly or continuously updated binaries;
- support for operating-system families beyond Windows, Linux, and macOS;
- turning DaD into a GitHub Action or publishing it in GitHub Marketplace; and
- changing commands, documents, JSON schemas, prompts, or other CLI behavior
  except for release-version reporting.

## Requirements

### Version authority

- **REL-VER-001:** A public release version must conform to Semantic
  Versioning 2.0.0.
- **REL-VER-002:** A release tag must be `v` followed by the complete semantic
  version, for example `v0.1.0` or `v1.0.0-rc.1`.
- **REL-VER-003:** The immutable release tag is the authoritative version for
  every artifact in that release. The repository must not require a separately
  maintained release-version constant or version file.
- **REL-VER-004:** `dad --version` must report `dad ` followed by the semantic
  version without the tag's `v` prefix for a release artifact.
- **REL-VER-005:** JSON version output and embedded prompt metadata must report
  the same semantic version as text version output.
- **REL-VER-006:** A build that cannot establish a valid release or versioned
  module version must identify itself as a development build and must not
  claim a public semantic version.
- **REL-VER-007:** Release automation must fail before publication when the
  built executable's text or JSON version differs from the release tag.
- **REL-VER-008:** Before version `1.0.0`, maintainers may change public
  contracts in a minor release but must identify breaking changes in the
  changelog. Beginning with `1.0.0`, incompatible changes require a major
  version increment, compatible functionality requires a minor increment, and
  compatible fixes require a patch increment.
- **REL-VER-009:** Public contracts considered during version selection
  include commands and options, exit codes, JSON schemas, generated document
  structure, lifecycle semantics, embedded official resources, and the release
  artifact contract.

### Changelog

- **REL-CHG-001:** `CHANGELOG.md` is the authoritative user-facing history of
  released changes.
- **REL-CHG-002:** The changelog must maintain an `Unreleased` section and use
  the applicable `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, and
  `Security` categories.
- **REL-CHG-003:** Every release tag must have a matching version heading and
  release date in `YYYY-MM-DD` form before publication.
- **REL-CHG-004:** Release notes must be derived from the matching curated
  changelog section. Commit messages and automatically generated commit lists
  are not authoritative release notes.
- **REL-CHG-005:** The release workflow must fail before publication when the
  matching changelog entry is absent, empty, or still marked unreleased.
- **REL-CHG-006:** Breaking changes, migration requirements, security-relevant
  changes, and known release limitations must be stated explicitly when
  applicable.

### Release source and trigger

- **REL-SRC-001:** A release build must use the exact source revision named by
  its release tag.
- **REL-SRC-002:** Publication automation must run only for tags matching the
  release-tag syntax. Pull requests, branches, and untagged commits must not
  publish a GitHub Release.
- **REL-SRC-003:** A tag must not be moved or reused after it has been pushed
  for release. A published version or asset must not be overwritten.
- **REL-SRC-004:** A correction to a defective release requires a new semantic
  version and tag. A release may be marked as a prerelease or deprecated
  without changing its artifacts.
- **REL-SRC-005:** The release configuration must support a local snapshot
  build that creates the complete artifact set without a tag, credentials, or
  publication.

### Validation gates

- **REL-CI-001:** Pull requests and changes to the primary branch must run
  formatting verification, `go vet ./...`, and `go test ./...`.
- **REL-CI-002:** Release validation must run native CLI tests on current
  supported GitHub-hosted Windows, Linux, and macOS environments.
- **REL-CI-003:** Windows validation must exercise native PowerShell and
  Command Prompt invocation without WSL. Linux and macOS validation must
  exercise a POSIX-compatible shell.
- **REL-CI-004:** Release publication must not begin unless every required
  native validation job succeeds for the tagged source revision.
- **REL-CI-005:** The release build must use the Go version declared by
  `go.mod`, or a compatible toolchain selected through Go's documented
  toolchain behavior.
- **REL-CI-006:** Snapshot validation must confirm the expected target set,
  archive names and contents, executable version behavior, checksum coverage,
  and absence of unplanned artifacts.
- **REL-CI-007:** The workflow and release configuration must pass their
  available syntax and configuration checks before publication.

### Supported artifacts

The initial release target set is:

| Operating system | Architecture | Executable | Archive |
| --- | --- | --- | --- |
| Linux | amd64 | `dad` | `tar.gz` |
| Linux | arm64 | `dad` | `tar.gz` |
| macOS | amd64 | `dad` | `tar.gz` |
| macOS | arm64 | `dad` | `tar.gz` |
| Windows | amd64 | `dad.exe` | `zip` |

- **REL-ART-001:** Every release must publish exactly one archive for each
  target in the table.
- **REL-ART-002:** Archive filenames must be
  `dad_VERSION_OS_ARCH.EXT`, using the semantic version without `v`,
  lowercase `linux`, `darwin`, and `windows` OS values, lowercase architecture
  values, and the archive extension from the table.
- **REL-ART-003:** Each archive must contain the target executable plus
  `README.md`, `LICENSE`, and `CHANGELOG.md` at its root.
- **REL-ART-004:** Release executables must be built from `./cmd/dad` with
  `CGO_ENABLED=0` and path trimming enabled.
- **REL-ART-005:** The executable name and behavior must remain equivalent
  across targets as required by SPEC-0001.
- **REL-ART-006:** Archive content, file modes, line endings, and paths must be
  usable by the target operating system and must not contain absolute paths,
  build-host paths, source-control metadata, or credentials.
- **REL-ART-007:** Windows arm64 and additional architectures require an
  approved revision of this specification before they become required release
  targets.

### Integrity and provenance

- **REL-INT-001:** Every release must include
  `dad_VERSION_checksums.txt` containing a SHA-256 checksum for every published
  target archive.
- **REL-INT-002:** The checksum file must use deterministic ordering and must
  not contain paths outside the release asset filenames.
- **REL-INT-003:** Every target archive and the checksum file must receive a
  GitHub artifact provenance attestation associated with the tagged source
  revision and release workflow.
- **REL-INT-004:** Release automation must use the workflow-scoped
  `GITHUB_TOKEN`; it must not require a maintainer's long-lived publication
  token.
- **REL-INT-005:** Workflow permissions must default to read-only. Only the
  release job may receive the minimum `contents`, identity-token, and
  attestation write permissions required for publication and provenance.
- **REL-INT-006:** Third-party GitHub Actions must be pinned to immutable full
  commit identifiers. Version comments may accompany those identifiers for
  maintainability.
- **REL-INT-007:** Secrets, credentials, and runner-specific paths must not
  appear in archives, checksums, release notes, logs intended as artifacts, or
  provenance subjects.

### Publication and installation

- **REL-PUB-001:** GitHub Releases is the primary initial distribution channel
  for release archives.
- **REL-PUB-002:** A stable release must use the matching tag as its release
  identifier, use `DaD VERSION` as its title, include the matching changelog
  section as release notes, and attach every required archive and checksum
  file.
- **REL-PUB-003:** A semantic prerelease must be marked as a GitHub prerelease.
  A stable semantic version must not be marked as a prerelease.
- **REL-PUB-004:** Repository immutable-release protection must be enabled when
  available. Regardless of hosting settings, the project policy forbids
  replacement of published tags and assets.
- **REL-PUB-005:** The README must document direct download, archive
  extraction, placement of `dad` on `PATH`, `dad --version` verification, and
  SHA-256 or provenance verification.
- **REL-PUB-006:** The README must disclose that initial binaries are unsigned
  and not notarized and may therefore produce platform reputation or
  quarantine warnings. It must not instruct users to disable operating-system
  security globally.
- **REL-PUB-007:** Versioned installation with
  `go install github.com/mahdiahmadirad/DaD/cmd/dad@VERSION` may be documented
  as a secondary source-build option. It must report the selected module
  version and must not be described as a prebuilt artifact.

## Interfaces and behavior

### Release preparation

Before creating a release tag, a maintainer:

1. confirms the intended revision satisfies its governing TASK;
2. selects the semantic version by reviewing changes to public contracts;
3. moves changelog entries from `Unreleased` into a matching dated version
   section;
4. verifies required CI checks on the intended revision; and
5. creates and pushes the immutable release tag.

The pushed tag starts validation and publication. A failed workflow publishes
no GitHub Release. A transient failure may be rerun against the unchanged tag;
a source or artifact correction requires a new version.

### Version resolution

A release artifact obtains its version from release-build metadata derived
from the tag. A versioned Go module build may obtain the equivalent version
from Go build information. All other builds report the development fallback.

Version resolution must be deterministic, must validate semantic-version
syntax, and must never inspect the network at runtime.

### Release assets

For an example `v0.1.0` release, the required assets are:

```text
dad_0.1.0_linux_amd64.tar.gz
dad_0.1.0_linux_arm64.tar.gz
dad_0.1.0_darwin_amd64.tar.gz
dad_0.1.0_darwin_arm64.tar.gz
dad_0.1.0_windows_amd64.zip
dad_0.1.0_checksums.txt
```

GitHub-generated source archives are not DaD release artifacts and are not
listed in the DaD checksum file.

### Failure and recovery

Validation, build, archive inspection, checksum, attestation, or upload failure
must make the release workflow fail. The workflow must not describe a partial
asset set as a successful release.

When a hosting failure leaves a draft or otherwise unpublished release, the
same workflow may retry publication for the unchanged tag and byte-identical
artifacts. Once a release is public, replacement requires a new version.

## Acceptance criteria

- Unit or command-level tests prove release, versioned-module, invalid, and
  development version resolution without network access.
- Text version output, JSON version output, and prompt metadata agree for the
  same build.
- CI passes natively on Windows, Linux, and macOS and exercises the shells
  required by SPEC-0001.
- A clean local snapshot produces exactly the five target archives and one
  checksum file with the required names.
- Automated inspection confirms every archive contains the correct executable,
  `README.md`, `LICENSE`, and `CHANGELOG.md`, and no unexpected root entries.
- Every checksum verifies the corresponding archive, and no required archive
  is omitted.
- Release configuration validation, `gofmt`, `go vet ./...`, and
  `go test ./...` pass.
- A publication workflow test or first release demonstrates that required
  assets are attached only after all validation gates succeed.
- The first published release demonstrates matching version output, changelog
  notes, tag, archive set, SHA-256 checksums, and provenance attestations.
- Installation instructions are manually exercised on Windows, Linux, and
  macOS; limitations and any unavailable architecture runtime checks are
  recorded.
- No signing, notarization, installer, package-manager, automatic-update,
  nightly-build, or extra-platform behavior is introduced.
