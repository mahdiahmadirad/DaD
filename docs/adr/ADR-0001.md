# ADR-0001: Implement the CLI in Go

## Status

Accepted

## Context

The DaD CLI must provide equivalent local behavior on Windows, Linux, and
macOS from one maintainable codebase. It must operate without a network,
version-control client, AI service, or platform-specific shell.

The repository has no existing implementation language. The initial CLI needs
deterministic filesystem behavior, embedded canonical resources, JSON and text
interfaces, safe process-level concurrency, and straightforward
cross-compilation.

## Decision

Implement the DaD CLI as one Go module using the Go standard library wherever
practical.

The public entry point is `cmd/dad`. Reusable behavior remains in internal
packages. Canonical templates, documentation rules, and official prompts are
embedded from their authoritative repository files at build time rather than
maintained as copied source strings.

The implementation must avoid conditional product behavior by platform.
Narrow platform-specific files are permitted only if a filesystem primitive
cannot be expressed portably; public command behavior remains identical.

## Consequences

- One source tree builds native executables for Windows, Linux, and macOS.
- The CLI has no runtime dependency on Go after compilation.
- Standard-library-first implementation limits dependency and supply-chain
  surface.
- Go's path and filesystem abstractions provide a common base, but tests must
  still exercise platform-specific path, rename, terminal, and process
  behavior.
- Contributors need a supported Go toolchain to build and test the CLI.
- Installation, signing, release packaging, and distribution remain separate
  concerns.

## Alternatives considered

### Python

Rejected for the initial CLI because it would require a compatible runtime or
additional executable packaging work on every supported platform.

### JavaScript on Node.js

Rejected for the initial CLI because it would require a compatible Node.js
runtime or additional executable packaging work.

### Rust

Rejected for the initial CLI because its additional implementation complexity
does not provide a necessary advantage for the current document and
filesystem-oriented command surface.
