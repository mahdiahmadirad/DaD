# ADR-0002: Automate tag-driven CLI releases

## Status

Proposed

## Context

DaD has a cross-platform Go CLI but no governed way to turn a reviewed source
revision into downloadable release artifacts. The CLI currently reports a
version maintained in source, and the repository has no tags, changelog,
release archives, checksums, or publication automation.

A release mechanism must build the same source for Windows, Linux, and macOS,
make the resulting artifacts easy to discover, and connect every published
binary to an immutable source revision. It must also keep release semantics in
the repository rather than in undocumented maintainer steps.

The core CLI is hosting-provider independent and operates without Git or
network access. Release infrastructure may integrate with a hosting provider,
but that integration must not become part of the framework or CLI runtime
semantics.

## Decision

Use a tag-driven release process in which:

- an immutable Git tag matching `vMAJOR.MINOR.PATCH` or an allowed Semantic
  Versioning prerelease identifies the source revision and authoritative
  release version;
- GitHub Actions performs native validation on Windows, Linux, and macOS and
  orchestrates publication;
- a repository-owned GoReleaser configuration builds, archives, checksums, and
  publishes the platform artifacts defined by the approved release
  specification;
- GitHub Releases is the initial public distribution channel;
- the curated repository changelog supplies the user-facing release notes; and
- release artifacts are published with SHA-256 checksums and GitHub build
  provenance attestations.

The release tag, not a manually maintained source constant, is authoritative
for a release build. Development builds use an explicit non-release version.
The implementation may additionally recover module version information for
versioned `go install` builds, provided it cannot cause a development build to
claim a published version incorrectly.

Release configuration and validation must be executable locally in a
non-publishing snapshot mode. GitHub-specific credentials and publication
steps remain isolated from portable build and verification behavior.

Published tags and release assets are immutable. A defective published release
is corrected by publishing a new version rather than moving a tag or replacing
an asset.

## Consequences

- Every downloadable artifact can be traced to one reviewed source revision
  and one semantic version.
- A single declarative build configuration produces consistently named
  archives and checksums for all supported targets.
- Native CI provides evidence for the three required operating-system
  families before publication.
- Maintainers must curate the changelog and create a valid release tag.
- Release publication depends on GitHub Actions and GitHub Releases, while the
  CLI and its semantics remain usable without GitHub.
- GoReleaser becomes a build-time release dependency, but not a runtime
  dependency of the CLI or the DaD framework.
- GitHub-hosted provenance improves verification but does not replace portable
  checksums.
- Unsigned initial archives can still trigger operating-system reputation or
  quarantine warnings. Signing and notarization require a later decision and
  task.
- Package-manager publication can consume the same release assets later
  without changing the initial distribution contract.

## Alternatives considered

### Hand-maintained release commands

Rejected because undocumented local commands make artifact selection, naming,
version injection, checksums, and publication difficult to reproduce and
review.

### A custom GitHub Actions build matrix without a release tool

Rejected for the initial release because it would require the repository to
implement and maintain archive naming, packaging, checksum generation,
changelog extraction, and GitHub Release upload behavior already provided by
GoReleaser. The workflow would also be harder to exercise locally.

### Package managers as the initial distribution channel

Rejected because each ecosystem adds separate manifests, review processes, and
publishing credentials. Stable GitHub Release assets are a simpler foundation
and can support package-manager publication in later tasks.

### Containers as the primary CLI distribution

Rejected because DaD operates directly on local project files and is intended
to be a native cross-platform executable. A container would add filesystem and
invocation complexity without replacing native distribution.

### Automatic version selection from conventional commits

Rejected because commit wording is not an approved compatibility decision.
Maintainers select the version by reviewing the public contracts and the
curated changelog before creating the release tag.
