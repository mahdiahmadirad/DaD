# TASK-0002: Define CLI release and distribution governance

## Status

Complete

## Outcome

Deliver review-ready repository authority for versioning, changelog
maintenance, cross-platform release artifacts, and GitHub-based CLI
distribution, together with bounded follow-up tasks for implementation and the
first public release.

## In scope

- Propose the architectural decision for tag-driven release automation.
- Draft the observable release and distribution contract.
- Define a task that implements and verifies the release automation without
  publishing a public release.
- Define a separate task that publishes and verifies the first public release.
- Record unresolved approval and implementation boundaries explicitly.

## Out of scope

- Accepting the proposed ADR or approving the draft SPEC.
- Implementing CI or release automation.
- Changing CLI version behavior.
- Creating a Git tag or GitHub Release.
- Publishing installers or package-manager packages.
- Signing or notarizing release artifacts.

## Constraints

- Preserve the agent-neutral, offline CLI semantics defined by the project
  vision and existing CLI contracts.
- Keep release authority in reviewed repository artifacts and immutable version
  control references.
- Do not claim release verification before the automation exists and a release
  is actually published.
- Approval authority remains with the project's human governance process.

## References

- [TASK-0001](TASK-0001.md) delivered the CLI and explicitly deferred
  packaging, release archives, publication, and CI to a later phase.
- [ADR-0001](../adr/ADR-0001.md) establishes the single Go codebase and
  cross-platform build constraints that the release design must preserve.
- [SPEC-0001](../specs/SPEC-0001.md) requires equivalent published behavior
  on Windows, Linux, and macOS and governs the existing version interface.
- [SPEC-0002](../specs/SPEC-0002.md) defines the CLI behavior and embedded
  release-resource expectations that distribution must preserve.

## Acceptance conditions

- One proposed ADR explains the selected release architecture, its
  consequences, and rejected alternatives.
- One draft SPEC defines version authority, changelog policy, release
  artifacts, supported targets, automation gates, integrity metadata, and
  immutability.
- Release automation implementation and first public publication are bounded
  by separate proposed tasks.
- Signing, notarization, installers, package managers, automatic updates, and
  other later distribution channels remain explicitly out of scope.
- All new document identifiers, statuses, sections, links, and references
  satisfy the repository documentation model.
