# ADR-0001: Persist accepted events before processing

## Status

Accepted

## Context

Partners retry webhook deliveries when acknowledgements are delayed or lost.
Downstream processing can also fail independently of request handling. Relay
must avoid both acknowledged event loss and duplicate downstream effects.

Handling the complete workflow inside the request would couple partner latency
to internal processing and leave recovery dependent on request logs.

## Decision

Relay will authenticate and validate each supported webhook, then persist its
event envelope in a durable inbox before acknowledging receipt.

The pair `(partner_id, event_id)` is the inbox identity and is unique. Internal
processing occurs after acknowledgement and records its own status. A repeated
delivery of an existing identity returns the original receipt without creating
another inbox event.

## Consequences

- An acknowledgement means Relay durably owns the accepted event.
- Partner retries do not create duplicate internal events.
- Downstream work can retry independently of the HTTP request.
- Storage availability becomes a requirement for accepting events.
- Inbox retention and failed-processing operations must be maintained.

## Alternatives considered

### Process before acknowledging

Rejected because processing latency and failures would increase partner
retries and make request handling responsible for recovery.

### Acknowledge before persistence

Rejected because a crash after acknowledgement could lose the event.

### Deduplicate only in downstream consumers

Rejected because every consumer would need to reproduce partner identity and
deduplication rules.
